1. Introduction

Welcome to AccessGuard. This software bridges the gap between your physical ZKTeco hardware terminals and your overarching Human Resources Oracle Database.

By constantly monitoring employee attendance and comparing it against designated shifts, AccessGuard automatically applies and lifts physical terminal lockouts based on tardiness policies, ensuring total compliance without manual HR intervention.

2. Backend & Reconciler Logic

The core of AccessGuard is the Reconciler Engine, an autonomous background service that computes employee tardiness and enforces physical door lockouts. It runs automatically on a scheduled timer, exactly once per day (usually configured for late at night). During this single daily run, it pulls down all the shift schedules and gate logs from your Oracle database to evaluate employee attendance for that day.

Configurable Rolling Window

Penalties are calculated on a strictly dynamic Rolling Penalty Window. Both the length of the window (e.g., 30 Days, 60 Days) and the allowed threshold (the Late Quota) are fully customizable via the system's Configuration module. Once an employee receives a "Late" strike, that strike automatically expires and is erased exactly when the configured window period ends.

How Strikes & Tiers Work

The Reconciler compares an employee's first daily punch against their scheduled shift start time. A Strike is recorded if they arrive after their shift's allowed grace period, or if their first scan of the day is a lunch return (Break-In without a Morning Check-in).

Based on their active strike count, employees are placed into one of three Tiers:

Clear
Strikes < Quota

Good standing. Assigned to Hardware Group 1, granting full 24-hour access to the physical doors.

Warning
Strikes == Quota

On probation. Stays in Hardware Group 1 (doors open normally), but is flagged in yellow on the HR Dashboard as one strike away from a lockout.

Locked Out
Strikes > Quota

Quota exceeded. Pushed instantly into Hardware Group 3 (a restricted, zero-access Time Zone). Doors reject their scans at all times until a Pardon is granted or an old strike naturally expires.

Behavioral example (30-day window, Late Quota = 2)

  1. Oct 1Employee punches in late. The terminal accepts the punch. That night, the Reconciler records 1 Strike (Clear Tier).
  2. Oct 15Employee punches in late. The terminal accepts the punch. That night, the Reconciler records 2 Strikes (Warning Tier). HR is warned on the dashboard.
  3. Oct 20Employee punches in late. The terminal accepts the punch. That night, the Reconciler records a 3rd strike (Locked Out Tier). The system pushes a zero-access Time Zone to the hardware, locking them out for tomorrow.
  4. Oct 21Employee arrives for work but is physically rejected by the terminal. HR grants a manual Pardon (Override). The Reconciler tags their newest strike, dropping their active count back to 2 (Warning Tier) and unlocking the doors for today. A built-in "Pardon Guard" shields them from acquiring any new strikes for the remainder of the day.
  5. Oct 31The very first strike from Oct 1 automatically expires! Their active count drops to 1, returning them to the Clear Tier.

Sequential Catch-up Mechanism

The Reconciler prioritizes perfect data integrity. If the AccessGuard server is turned off or loses connection over a weekend or holiday, it will never skip days. Upon startup, it utilizes a while loop to detect the last successfully processed date and calculates every missed day individually, in chronological order, until it is fully caught up with the present day.

Database Sync→Catch-up Missing Days→Process Today→Apply Terminal Lockouts

Hardware Signature (HWID) Security

AccessGuard uses an advanced piracy prevention system. A unique signature (HWID) is generated using the host server's Motherboard and CPU serials. This ensures your license cannot be cloned to unauthorized servers. (Note: Upgrading RAM or GPUs will not invalidate your license, but moving the OS drive to a new Motherboard will require a new activation key).

3. Dashboard Module

The Dashboard is the operational center of AccessGuard, providing a real-time, high-level overview of your entire workforce. The core of this page is the Employee Table, which accurately reflects every employee's current standing based on the nightly Reconciler calculations.

The Employee Table

This table tracks exactly how close an employee is to losing their physical access. It features live search and a toggle to filter out exempt staff.

Employee ID
The unique identifier for the employee, synchronized directly from your Oracle database.
Status (Penalty Tier)

Displays the exact tier the employee currently belongs to. This directly determines their physical hardware access.

  • Clear: Employee has fewer strikes than the Late Quota limit. Full physical access.
  • Warning: Employee is one strike away from a lockout. Full physical access, but HR is alerted.
  • Locked Out: Employee has exceeded the Late Quota. Hardware access is completely revoked.
Lates in Window
A counter showing the exact number of active "strikes" an employee currently has against the limit. Example: 3 / 3 means they have reached the limit (Warning tier), and a 4th time will trigger a lockout.
Window Expires
Displays a dynamic countdown showing how many days are left until their oldest active strike naturally "falls off" their record. Example: in 14 days.
Last Late
The precise date of their most recent tardiness infraction.
Last Pardoned
If HR previously pardoned this employee, this displays the date the pardon was granted. This is crucial for tracking chronic abusers of the Override module.

Manual Reconciler Trigger

Normally, the Reconciler runs completely automatically at the configured time every single night. However, if you recently reconnected a broken database or need to instantly calculate strikes midway through a shift, you can press the Run Reconciler button on the top right of the dashboard. This forces the engine to instantly wake up, pull down the latest hardware punches from Oracle, and instantly update the status of every employee on this table.

4. Override Module (Pardons)

The Override module allows HR administrators to manually bypass the Reconciler's automated logic and forgive an employee's tardiness. When an employee is locked out, authorized HR staff can grant a Pardon to immediately restore their physical access.

What exactly happens when a Pardon is granted?

When you click "Pardon" on the Override dashboard and provide a valid reason, the backend executes the following exact sequence instantly:

  1. Active Strike Reduction: The system identifies the employee's most recent "Late" strike and tags it internally as Pardoned. This instantly drops their active strike count by 1.
  2. Instant Hardware Unlock: Because their active strike count drops below the Late Quota, they immediately return to the Warning Tier. The backend instantly pushes an Access Group 1 (Full Access) update to the ZKTeco terminals over the network, unlocking the doors immediately.
  3. The Pardon Guard: The employee is granted a digital shield for the remainder of the current day.
  4. Audit Logging: The timestamp, HR admin's username, and the text reason are permanently recorded in the Override Audit Log for accountability.

The "Pardon Guard" (Double-Penalty Protection)

Because the Reconciler Engine runs autonomously every night, there is a risk that it could see the late punch from the morning and penalize the employee again that night, effectively locking them out twice for the same infraction.

To prevent this, AccessGuard employs a strict Pardon Guard. When a pardon is issued, the system records the exact date. When the Reconciler Engine runs that night, it checks if a pardon was granted today. If it was, the Reconciler completely skips late-count evaluation for that employee for that specific day. This guarantees that an employee who was pardoned in the morning can safely clock in the next day without being unfairly re-locked out.

5. Configuration Settings

This module dictates the strict mathematical rules the Reconciler Engine enforces. Every setting directly impacts when an employee is penalized. It is divided into three critical sections: Global Settings, Shift Schedules, and Employee Exceptions.

1. Global Settings

These settings define the baseline rules for all employees across the organization.

Default Grace Period (minutes)
5

The universal buffer added to the official shift start time before an entry is marked as "Late". This applies to anyone who does not have a custom Shift or Exception override.

Penalty Window (days)
30

The dynamic timeframe in which late arrivals are tracked before they expire. A strike recorded today will be wiped exactly X days from today.

Late Quota
1

The exact number of late arrivals allowed within the Penalty Window before a lockout is triggered. Exceeding this triggers a Lockout.

Reconciler Run Time
01:00 AM

The exact daily schedule the autonomous background service runs to sync Oracle data and calculate strikes.

2. Shift Schedules

AccessGuard automatically discovers unique shifts (e.g., "08:00 to 16:30") directly from your Oracle database during the nightly sync. HR administrators can click "Edit" on any discovered shift to customize its specific behavior:

Grace (min)
15

A shift-specific grace period that overrides the Global Default. For example, Night Shifts might allow 15 minutes instead of the global 5.

Lunch Start & Lunch End
12:0013:00

Optional time bounds. If configured, the Reconciler expects a "Break-In" punch (returning from lunch) and will penalize employees who return after the Lunch End time plus the Grace period. Leave empty for no lunch tracking.

3. Employee Exceptions

This section allows you to override the rules on a per-employee basis.

Custom Grace (min)
30

An employee-specific grace period. This is the highest priority setting and completely overrides both the Global Default and their Shift Schedule.

Exempt from penalties
✓ CHECKED

A master override switch. If checked, the Reconciler will permanently ignore all late arrivals and missing punches for this specific employee. They will always remain in the Clear Tier.

6. Terminals Module

This tab manages concurrent IP connections to all your physical ZKTeco hardware terminals via the TerminalConnectionManager.

Access Group Pushing

Rather than using generic "Enable" or "Disable" commands, AccessGuard leverages the hardware's native Access Group architecture. Depending on the employee's penalty tier, the system pushes either Group 1 (Clear/Warning - Full Access) or Group 3 (Locked Out - Zero Access) over the network.

Automated Clock Synchronization

A critical feature managed through these connections is automated time alignment. Before every Reconciler cycle (or whenever a terminal reconnects), the ClockSyncService queries the terminal's internal clock. If it detects a time drift of more than 60 seconds compared to the server's authoritative time, AccessGuard automatically overwrites the hardware clock. This guarantees absolute precision for calculating grace periods and prevents hardware drift from unfairly penalizing employees.

7. Database Module

This module houses the connection strings and authentication for your central Oracle HR Database. AccessGuard relies on a direct connection to your Oracle database to calculate penalties.

Configuration Fields & Setup Guide

To establish a connection, you must provide the following standard Oracle credentials in the Database tab. If you are unsure of these values, they can typically be found in your organization's tnsnames.ora file or by contacting your Database Administrator.

  • Host / IP Address: The network address of your Oracle server. Open Command Prompt and ping your database hostname to find the IP if necessary.
  • Port: The Oracle listener port (the default is almost always 1521).
  • Service Name / SID: The specific database identifier (e.g., XE or ORCL). You can find this in your Oracle SQL Developer connection properties.
  • Username & Password: Credentials for a read-only database user (e.g., system).

Required Oracle Tables (Schema)

The Reconciler Engine requires two strictly-named tables (or views) to exist in your Oracle database. If your schema uses different table names, you must create Database Views matching these exact names and column structures so AccessGuard can query them successfully.

1. Shift Schedule Data: MDPL_EMP_SHIFT_V

The system needs a mapping that tells it what time each employee is supposed to arrive. This must be accessible via a view or table named MDPL_EMP_SHIFT_V.

Required Column Name Expected Format / Description
MACHINE_ID The physical enrollment ID from the ZKTeco device (e.g. "1001"). Used to link the person to their schedule.
EMPLOYEE_NUMBER The internal HR payroll ID (used for reference in HR audit logs).
SHIFT_START Expected format: HH:mm (e.g. "08:00"). Crucial for calculating late grace periods.
SHIFT_END Expected format: HH:mm (e.g. "16:30").

2. Raw Terminal Punch Data: PP_EMP_ATT_MST_DW

The system requires a continuous stream of the actual scans happening at the physical doors. This must be accessible via a view or table named PP_EMP_ATT_MST_DW.

Required Column Name Expected Format / Description
AM_EMPNO The physical enrollment ID from the ZKTeco device (matches MACHINE_ID).
AM_TIME CRITICAL: Must strictly follow the string format YYYY/MM/DD HH24:MI (e.g. "2026/10/08 08:05") so the Reconciler can accurately calculate tardiness.
AM_SHIFT The ZKTeco punch state code. Must be '1' for Morning Check-In and '3' for Break-In (Lunch Return).

8. Reports Module

The reporting engine is designed for HR and auditing staff to track system accountability, manual overrides, and raw hardware interactions. Every table in this module can be filtered by Date and exported directly to CSV for external processing or payroll deduction.

1. Override Audit Log

This table tracks every time an HR administrator manually bypasses the system's lockouts (Pardons). It is updated instantly the moment an admin clicks "Pardon" on the Override page.

Column Name Description
Timestamp The exact date and time the pardon was granted.
Employee ID The ZKTeco ID of the employee who was pardoned.
Late Days The number of active strikes the employee had at the exact moment they were pardoned.
Approved By The username of the admin who granted the pardon. Crucial for accountability.
Reason The text explanation provided by the admin (e.g., "Car broke down", "Approved by Manager").

2. System Audit Log

This table records critical configuration changes and security events within the AccessGuard dashboard itself. It is updated automatically by the backend whenever a sensitive action occurs.

Column Name Description
Timestamp When the action occurred.
Action The category of the event (e.g., "UserLogin", "ConfigUpdate", "PardonGranted").
Username The admin account that performed the action.
Details Contextual information (e.g., "Updated Late Quota from 3 to 4").

3. Raw Punch Logs

This table provides a direct window into your central Oracle database. It is not generated by AccessGuard; rather, it is a live query of the physical hardware scans synced to Oracle.

Column Name Description
Timestamp The exact time the employee physically scanned their finger or card.
Employee ID The employee's ZKTeco ID.
Event Type The punch state code. Shows whether the scan was a "Check-In" (Morning) or a "Break-In" (Lunch return).
Location The physical terminal location (defaults to Unknown if not mapped in Oracle).

4. Historical Lates

This table shows the permanent history of an employee's tardiness. Unlike the active "Dashboard" (which clears strikes when the rolling window expires), this table permanently stores every infraction.

Column Name Description
Date The actual day the employee was late.
Status Will display "Counted" (an active, enforced strike). Can also display "Pardoned" if the record was overridden via the Override Module.
Recorded At The exact timestamp when the Reconciler Engine caught the infraction during its nightly run.

9. Admin Users Module

AccessGuard uses strict Role-Based Access Control (RBAC) to ensure that only authorized personnel can make changes to physical security and system configurations. The Admin Users module allows you to provision, edit, and revoke access to the web dashboard.

Adding, Editing, & Revoking

You can create new system accounts or edit existing ones. The system enforces a minimum 8-character password policy for all accounts. When an employee leaves the HR or IT department, you can instantly revoke their access by deleting their account from the Registered Users table.

Granular Permissions

Instead of relying on blanket administrator roles, AccessGuard allows you to configure exact privileges for each account. The available permissions are:

Administrator
Grants unrestricted access to all modules and system settings. Overrides all other toggles.
Can Override Penalties
Allows HR staff to grant Pardons/Overrides and instantly unlock doors, without giving them the ability to change system rules.
Can Edit Config
Allows the user to change the core Reconciler rules (e.g., Late Quota, Rolling Window length, and Grace Periods).
Can Manage Terminals
Allows the user to enroll new ZKTeco hardware IPs or remove offline devices.
Can Manage Database
Restricts access to the Oracle connection strings and credentials to authorized IT staff only.
Can View Reports
A read-only permission allowing payroll or auditing staff to export historical lockout and attendance data to CSV.

Only users who authenticate with these specific permissions can interact with the protected backend API endpoints.
